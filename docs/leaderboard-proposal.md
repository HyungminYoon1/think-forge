# 전체 사용자 랭킹 서버 제안

상태: **DESIGN ONLY — NOT_IMPLEMENTED / NOT_DEPLOYED**. 2026-10-08 기준 공식 문서 확인. 이번 작업에서는 Neon 프로젝트, DB, Cloudflare Worker, 계정 또는 유료 리소스를 만들지 않았습니다. 네 사이트는 독립적으로 플레이할 수 있으며 현재 기록은 기기에만 남습니다.

## 권장 구성

게임마다 서버와 DB를 만들기보다 검증 API 하나와 Neon PostgreSQL DB 하나를 공유합니다. Neon은 저장소이지 점수 제출을 판정하는 애플리케이션 서버가 아닙니다.

```text
GitHub Pages
  THINK FORGE / ORBIT COURIER / LIGHT ROUTE / POCKET CITY
             ↓ HTTPS
공통 Cloudflare Workers API
  익명 사용자 · 실행 티켓 · 행동 검증 · 서버 점수 계산
             ↓ 서버에만 저장한 연결 자격증명
Neon PostgreSQL
  실행 기록 · 게임별 최고 기록 · 시즌별 랭킹
```

정적 Pages 호스팅과 현재 순수 모델 계층은 유지합니다. 새 백엔드는 별도 저장소가 적절합니다. 현재 파일에 DB 연결 문자열을 넣거나 브라우저에서 DB에 직접 접근하지 않습니다.

| 비교                 | 의견                                                                            |
| -------------------- | ------------------------------------------------------------------------------- |
| 게임별 서버·DB 3개   | 배포·보안·쿼터 관리가 중복되어 초기 규모에는 불필요                             |
| 공통 Workers + Neon  | 현재 순수 JS 규칙 재사용과 관계형 집계에 적합한 추천안                          |
| 공통 Workers + D1    | PostgreSQL이 필요하지 않다면 검토할 대안. 이번에는 별도 조사·선택·생성하지 않음 |
| 점수만 POST하여 저장 | 개발자 도구로 점수를 바꿀 수 있어 경쟁 랭킹에는 부적합                          |

## 같은 조건끼리 비교

랭킹 키는 `game_id + rules_version + content_version + mode + seed/season`입니다. 다른 구간·문제 난이도·퍼즐 코드·규칙 버전을 한 순위표에 섞지 않습니다.

- ORBIT COURIER: 항로 코드와 구간별 점수. 전체 배송 합산은 동일한 세트 완주 규칙을 별도로 정의.
- LIGHT ROUTE: 퍼즐 코드와 단계별 점수, 동점은 조작·힌트 횟수 순서.
- POCKET CITY: 도시 코드별 20턴 완료 점수, 같은 카드 순서끼리 비교.
- THINK FORGE: 우선 개인 학습 도구로 유지. 경쟁 모드를 연결한다면 같은 문제 세트·범주·단계·시간 규칙을 고정. 화면에 풀이가 공개되는 학습 모드를 랭킹에 포함하지 않음.
- 오늘의 경쟁 판은 서버의 UTC 날짜로 발급하고 한국어 화면에 마감 시각을 표시. 현재 문제은행의 로컬 날짜 도전과 동일한 제도라고 취급하지 않음.

## 제출 흐름과 API 초안

1. 브라우저가 익명 식별자를 등록하고 서버가 제출용 토큰을 발급합니다. 공개 닉네임은 선택 사항이며 이메일·실명·소셜 로그인은 초기 버전에서 수집하지 않습니다.
2. 서버가 `POST /v1/runs`에서 한 번 쓰는 실행 티켓, 서버 선택 seed/버전, 제한 시간과 시작 조건을 발급합니다.
3. 클라이언트는 순서가 있는 행동만 기록합니다. 플레이 자체는 서버가 잠시 unavailable이어도 기기 기록 모드로 계속됩니다.
4. `POST /v1/runs/:id/finish`는 티켓과 행동을 받아 서버가 규칙을 재생하고 점수를 계산합니다. 제출된 score 필드는 받지 않거나 무시합니다.
5. DB 트랜잭션 하나에서 티켓 소진·결과 저장·개인 최고 갱신을 처리합니다.
6. `GET /v1/leaderboards`는 검증된 상위 기록만 제공합니다. 읽기는 짧게 캐시하고 무제한 페이지 탐색을 허용하지 않습니다.

| 게임      | 제출할 행동                        | 서버 검증                                             |
| --------- | ---------------------------------- | ----------------------------------------------------- |
| 궤도 택배 | 각도·추진력·시도·힌트 사용         | 고정 시간 간격 물리 계산, 도착 판정과 점수 재계산     |
| 빛의 미궁 | 장치 좌표, 회전·되돌리기·힌트 순서 | 초기 판 재생, 모든 목표의 색과 도달 판정, 비용 재계산 |
| 도시      | offer index·토지 좌표·휴식 순서    | 20턴 재생, 예산·건설 적법성, 전력·환경·인접 점수      |
| 문제 도전 | 각 문제의 답·제출 순서             | 서버 생성 문제로 정답률 재계산, 전체 제한 시간 확인   |

궤도 게임은 티켓을 받은 뒤의 모든 시도를 서버에 연결해야 시도 횟수를 검증할 수 있습니다. 오프라인으로 성공한 값만 제출하면 실패 시도나 힌트 사용을 숨길 수 있습니다. 힌트를 사용하는 경쟁 모드는 힌트 발급도 서버가 기록해야 합니다. 기기 기록을 그대로 검증된 랭킹으로 승격하지 않습니다.

## 데이터 모델 초안

- `players`: 내부 익명 UUID, 공개 별명, 토큰 해시, 생성/삭제 시각.
- `runs`: UUID 기본 키, 플레이어, 게임·버전·모드·seed, 티켓 해시, 발급/만료 시각, 상태, 제출 해시, 검증 결과, 점수.
- `best_scores`: 비교 키와 플레이어를 합친 UNIQUE 키, 검증된 run 참조와 점수.
- `seasons`: 기간과 허용된 게임·버전·판, 활성 상태.
- 점수 내림차순과 필요한 동점 기준을 포함한 집계 인덱스. 순위는 조회 시 계산하며 유효하지 않은 결과는 제외.

같은 run의 동일한 제출 해시는 기존 결과를 돌려주고, 다른 행동으로 재제출하면 거부합니다. 단순한 클라이언트 UUID만으로 중복 방지를 끝내지 않습니다. 티켓을 선점하는 원자적 조건부 갱신과 UNIQUE 제약을 함께 사용합니다. HTTP serverless driver의 트랜잭션과 동시 제출 경쟁은 통합 시험이 필요합니다.

## 기본 방어와 남는 한계

- 허용 게임·버전·seed 형식, 행동 종류·횟수·순서, 만료·소유권 검증.
- 요청 본문 32KB, 게임별 행동 수 상한 등 작은 한도를 우선 설정. 실제 궤도 모드 로그 요구량에 맞게 부하 시험 후 확정.
- 매개변수화 SQL, 닉네임 길이·문자 제한, 화면에는 textContent로 표시.
- 자격증명은 Worker secrets에만 보관. API/DB 로그에 토큰·연결 문자열·전체 요청을 출력하지 않음.
- CORS는 GitHub Pages 출처를 제한하지만 인증 수단은 아님. 같은 계정의 프로젝트 Pages는 모두 `https://hyungminyoon1.github.io` 출처를 공유하므로 경로로 출처를 구별하지 못함.
- 토큰/짧은 기간 식별자별 속도 제한과 전체 서비스 제출 한도를 함께 사용. Workers 지역별 제한만으로 엄격한 글로벌 한도를 보장하지 않으므로 원자적 DB 카운터나 별도 직렬화 계층이 필요.
- 개인 최고 순위만 노출하고 익명 식별자는 공개하지 않음. 삭제 기능은 본인 토큰으로 확인하고 기기 토큰을 잃으면 복구가 어렵다는 점을 고지.
- 규칙 재생은 조작된 점수·불가능한 행동을 막지만 봇·자동 풀이·여러 익명 계정·공개된 정답을 완전히 막지 못함. 사람이 실력으로 플레이했다는 인증이 아니며 상금/공식 시험 시스템으로 홍보하지 않음.
- 브라우저가 보고한 반응 시간이나 힌트 사용 여부만으로 경쟁 결과를 인증하지 않음. 문제를 미리 모두 보내는 방식에서는 답 자동 계산도 가능하므로 문제 공개 시점과 시간 판정은 별도 설계.

## 보존 정책 제안 — 연결 전에 검토 필요

현재 확정된 운영 정책이 아니라 초기 검토안입니다.

- 미완료 티켓은 30분 이내 만료, 상세 행동 로그는 7일 후 삭제.
- 표시 시즌은 30일, 검증 결과는 90일 이후 삭제/최소 집계.
- 닉네임과 개인 기록 삭제 요청 기능 제공. 마지막 이용 후 장기 방치 계정은 별도 정책을 확정.
- 원시 IP 장기 저장을 피하고 단기 rate-limit 키가 필요하면 회전 해시 사용. 제공자 자체 로그 보존 설정도 확인.
- DB 백업·복원 방법과 삭제 반영 시점을 정한 후 공개 수집 시작.

## 무료 운영의 조건과 중단 방식

공식 문서상 확인한 한도입니다. 계정에 다른 프로젝트/Worker가 있으면 적용 단위와 현재 사용량을 따로 확인해야 합니다.

| 서비스         | 확인한 Free 한도                                        | 설계 영향                                           |
| -------------- | ------------------------------------------------------- | --------------------------------------------------- |
| Neon           | 프로젝트별 100 CU-hours/월, 1GB DB, 5GB egress/월       | 대용량 행동·상시 조회 제한, 사용량 알림과 중단 필요 |
| Neon 자동 정지 | 5분 유휴 후 scale-to-zero                               | 간헐적 사용에 유리. 연결 재개 지연 고려             |
| Workers        | 계정 합계 100,000요청/일, 요청당 CPU 10ms, 메모리 128MB | 재생·항로 생성의 실제 CPU 비용을 측정해야 함        |

0.25 CU에서 100 CU-hours는 활성 시간 약 400시간입니다. 연속 접속으로 한 달 내내 DB를 깨워두면 무료 한도를 초과할 수 있으므로 무료라는 말은 무제한/항상 가동을 의미하지 않습니다. Neon의 compute/egress 소진은 다음 주기 또는 업그레이드까지 정지될 수 있고 storage 소진은 쓰기를 막습니다. Workers 일일 무료 요청 초과도 오류가 나며 UTC 자정(한국 09시)에 초기화됩니다.

무료 플랜 유지, 자동 유료 전환/유료 업그레이드 금지, 사용량 임계점에서 랭킹 API만 unavailable/429 처리하는 것이 초기 추천입니다. 가용 한도 80%부터 신규 경쟁 실행을 줄이고 잔여 20%는 결과·삭제 요청 처리에 남기는 안을 제안합니다. 이 비율과 하루 제출 수는 실제 사용량과 런타임 측정 뒤 확정합니다. 이미 발급한 티켓의 처리 정책도 정해야 합니다. 기기 내 게임은 이 중단과 독립적으로 계속 작동합니다.

현재 Node 시험 통과는 Workers CPU 10ms 충족이나 Neon 통합 검증을 증명하지 않습니다. 특히 궤도 목표 생성 후보 탐색은 미리 생성/검증한 시즌 판을 사용하거나 캐시해 CPU 비용을 줄일 수 있습니다. 무료 CPU로 충분하지 않으면 유료 전환을 자동으로 실행하지 말고 API를 중단하거나 서버 선택을 다시 검토합니다.

## 실제 구축 순서

1. 별도 API 저장소, 공개 데이터·보존·무료 중단 정책 확정.
2. Neon Free 새 프로젝트와 전용 최소 권한 역할, SQL migration, 복구 절차 준비.
3. Workers Free API, secrets, 입력·속도 제한, ticket/submit 트랜잭션 구현.
4. 세 게임의 순수 규칙을 버전 고정 모듈로 재사용하고 서버 재생 시험.
5. 위조 점수·중복 동시 제출·만료·잘못된 행동·쿼터 중단·삭제·CPU/DB 비용 통합 시험.
6. Pages에 선택적 API client를 연결하고 CSP connect-src에 정확한 API만 추가. 서버 장애 때 기기 기록 모드 유지.
7. 작은 비공개 시험 → 공개 랭킹. 서버 검증된 기록만 별도 배지로 표시.

Neon 콘솔 방문과 새 DB 생성은 위 정책과 API 구축을 실제로 진행할 때 필요합니다. 이번 정적 게임 배포에는 필요하지 않습니다.
